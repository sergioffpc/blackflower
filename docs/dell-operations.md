# Dell LAN infrastructure

[Issue #45](https://github.com/sergioffpc/blackflower/issues/45) establishes
Git-to-LAN infrastructure with a diagnostic UDP workload. The diagnostic is not
the simulation server and provides no simulation, content or performance
acceptance evidence. The deployment architecture is defined by
[issue #44](https://github.com/sergioffpc/blackflower/issues/44).

## Host and network

The operator confirmed the DHCP change and absence of allocations in the MetalLB
pool before provisioning. Observed host and selected setup inputs:

| Item                                | Value                                                           |
| ----------------------------------- | --------------------------------------------------------------- |
| Host                                | Dell PowerEdge R630, hostname R630, Kubernetes node dell        |
| Operating system                    | Debian 13.6, kernel 6.12.107+deb13-amd64                        |
| CPU and memory                      | Two Xeon E5-2690 v4, 28 physical cores, 56 threads, 256 GB      |
| Administrative access               | Local user sc with sudo; SSH on the LAN                         |
| Interface and reserved host address | eno1, 192.168.86.46/24                                          |
| Router                              | Google Mesh, 192.168.86.1                                       |
| DHCP pool                           | 192.168.86.20–192.168.86.199                                    |
| MetalLB pool                        | 192.168.86.200–192.168.86.239; explicit pool selection required |
| Common service port                 | UDP 27015                                                       |
| LAN DNS                             | BIND on 192.168.86.46:53, zone blackflower.home.arpa            |
| Pod and Service networks            | 10.42.0.0/16 and 10.43.0.0/16                                   |

The IPv4-only cluster uses single-node K3s directly on Debian. Traefik,
ServiceLB and metrics-server are disabled. MetalLB advertises on eno1 using
layer 2. No router port forwarding is required. UDP data NodePorts are disabled.
Kubernetes allocates a TCP health-check NodePort for the Local traffic policy;
the firewall restricts the NodePort range to LAN clients. A dedicated nftables
table filters non-LAN ingress before Kubernetes DNAT and leaves other firewall
tables intact. BIND accepts only loopback, LAN and pod clients; IPv6 DNS is
disabled. Kubernetes credentials remain root-readable.

## Package installation policy

Prefer APT for every host package. Use the upstream project's official release
only when a compatible APT package is unavailable. Recheck package availability
before installing or upgrading. The bootstrap stops for review if a K3s APT
candidate appears so its version and packaging can be reviewed before use.

At provisioning time, configured Debian repositories had no K3s or Flux
packages. The bootstrap uses the checksum-verified official binary for K3s
v1.36.4+k3s1 in /usr/local/bin. It is not updated by `apt upgrade`. Flux runs as
controllers inside K3s; its CLI is not needed on the host. BIND and its
utilities are installed using APT without recommended packages; nftables and DNS
query tools were already installed.

Development dependencies and code checks run inside the existing pinned
[devcontainer](../.devcontainer/devcontainer.json) or CI. Do not install uv,
additional Node versions, compilers, formatters, Git LFS or container runtimes
on the server for source validation. K3s already supplies containerd.

The state templates pin Flux v2.9.5, MetalLB v0.16.0, ExternalDNS v0.22.0 and
the Kubernetes agnhost diagnostic 2.66.1. The last two images use immutable
registry digests. `gotk-components.yaml` is generated by `flux install --export`
inside a development container with only the source and Kustomize controllers.
`controllers/metallb.yaml` is the unmodified upstream v0.16.0 native manifest,
SHA-256 `b0b9be2802f10aa32d45308b4457d06cde0c70544712c8d0cf5511657ffd2b69`.

## Initial bootstrap

Read and adapt the source files in [deploy/dell](../deploy/dell) before use on
another host. Confirm the interface, subnet, host reservation and unused pool.
The host installer refuses existing K3s or BIND configuration. It is an initial
provisioning tool, not an upgrade or recovery command.

```shell
sudo bash deploy/dell/bootstrap-host.sh
sudo k3s kubectl get nodes
sudo bash deploy/dell/provision-dns-secret.sh
```

The DNS provisioning script copies the locally generated TSIG key into the
external-dns/rfc2136 Secret without printing it or placing it in process
arguments. K3s encrypts Secrets at rest. The key authorizes only A, AAAA and TXT
changes and authenticated zone transfers in blackflower.home.arpa. ExternalDNS
requires the blackflower.io/dns annotation, filters that domain, and owns
records using a fixed TXT owner ID. Unrelated DNS records remain outside its
ownership.

Set up a dedicated SSH signing key outside the checkout, configure the Git
identity, and register the public key as a GitHub signing key. Keep the private
key and trusted allowed-signers file outside the public repository. Provision a
repository-scoped Contents-write credential for the operator; Flux requires no
GitHub token or deploy key for this public source. Never put tokens or signing
keys in manifests, images or Git history.

Prepare a separate new operational checkout using absolute paths:

```shell
bash deploy/dell/bootstrap-state.sh /home/sc/blackflower-gitops \
  /home/sc/.local/share/blackflower/git-signing \
  /home/sc/.local/share/blackflower/allowed_signers
```

Inspect the signed state commit and rendered manifests before the first push.
The new branch has independent history and contains no workflows or source build
triggers. Enable branch protection against force pushes and deletion, require
signed commits, and allow direct operational updates without a PR. Keep
main/develop protections unchanged.

```shell
git -C /home/sc/blackflower-gitops verify-commit HEAD
git -C /home/sc/blackflower-gitops push -u origin gitops
sudo k3s kubectl apply --server-side \
  -f deploy/dell/state/flux-system/gotk-components.yaml
sudo k3s kubectl wait --for=condition=Established --timeout=60s \
  crd/gitrepositories.source.toolkit.fluxcd.io \
  crd/kustomizations.kustomize.toolkit.fluxcd.io
sudo k3s kubectl apply -f deploy/dell/state/flux-system/sync.yaml
sudo k3s kubectl -n flux-system get gitrepositories,kustomizations
```

Flux owns its controllers and reconciles infrastructure controllers before the
address pool, then environments. Infrastructure pruning is disabled; environment
pruning is enabled. K3s's packaged CoreDNS and local-path provisioner are not
part of the environment inventory. No Git webhook receiver is exposed.

## Google Mesh integration

First verify `dig @192.168.86.46 ns.blackflower.home.arpa` and public DNS
through the Dell. In Google Home, open Wi-Fi settings, Advanced networking, DNS,
Custom, and use 192.168.86.46 as the DNS server. Do this only after the Dell
resolver is healthy. A public secondary resolver cannot resolve the private zone
and is not a reliable fallback for it. A second private resolver is future work.

Google Mesh forwards client queries to the custom resolver. BIND forwards
external domains to 1.1.1.1 and 9.9.9.9, never back to the Mesh, avoiding a
forwarding loop. Clients using independent encrypted DNS may bypass LAN DNS.
Verify the actual client path; a direct query to the Dell alone does not prove
that the Mesh integration works.

This makes the Dell a DNS availability dependency for the LAN. If it is down,
restore the previous Google Mesh DNS setting for ordinary Internet resolution;
Blackflower names require restoration of the private resolver.

## Functional demonstration

The agreed test boundary is a signed Git update through observable LAN DNS and
UDP. No C++ simulation behavior changes in this issue. Validate shell scripts,
rendered manifests and documentation in the devcontainer; use the live steps
below for the deployment boundary.

-   Copy the source diagnostic directory into the operational checkout's
    environments/diagnostic directory and add `diagnostic` to the environments
    Kustomize resources list.

-   Commit as `feat(gitops): expose diagnostic UDP service`, verify the
    signature and push. Wait for environments to become Ready at that commit
    revision.

-   On a LAN client, run `bash deploy/dell/verify-lan.sh diagnostic-v1`. Record
    the Git revision, allocated IP, DNS resolver, client identity and response.

-   Change the pod hostname in operational desired state to diagnostic-v2,
    commit as `chore(gitops): update diagnostic response`, verify and push.
    After Flux reconciles, run the probe with diagnostic-v2. The Service is
    unchanged and retains its allocated IP.

-   Remove diagnostic from the operational Kustomize resources list, commit as
    `chore(gitops): remove diagnostic service`, verify and push. Run the probe
    with absent after Flux pruning and DNS TTL expiry. Verify both the Service
    and exclusive namespace are absent, the address is unallocated, and
    unrelated resources retain their UIDs. Keep shared infrastructure present.

ExternalDNS reconciles every 15 seconds, Flux fetches every 30 seconds, and the
record TTL is 30 seconds. Record observed timings rather than assuming these
intervals guarantee completion. Running the probe on the Dell tests a LAN
address path but does not establish layer-2 reachability from another machine;
obtain a second LAN client's result for that evidence.

## Access, recovery and upgrades

Use `sudo k3s kubectl` on the Dell. For a remote administrator, securely
provision a kubeconfig and trust the existing API certificate for the reserved
address. Do not make the kubeconfig world-readable or publish it. Inspect Flux
conditions and logs, ExternalDNS logs, Services, pods and MetalLB events with
kubectl; `sudo journalctl -u k3s -u named` covers host services.

Restore a workload by reverting its desired-state commit, signing the revert,
verifying it and pushing. Flux retains recovery because Git contains the
restored state. Do not use an unrecorded kubectl change as durable recovery.
Automatic image publication and writers are outside issue #45.

For host recovery, keep encrypted backups outside the public repository of
/etc/rancher/k3s, /var/lib/rancher/k3s/server, /etc/bind, /var/lib/bind and the
operator's credentials and signing trust. With the default SQLite datastore,
stop K3s while copying its database and preserve the server token and encryption
configuration. Synchronize BIND's journal with `sudo rndc sync` before its
backup. Restore host files and permissions to the reserved address before
starting services. Do not run the initial bootstrap over restored configuration.

Alternatively rebuild an empty cluster from the protected gitops branch: restore
or rotate the DNS TSIG credential, recreate its Kubernetes Secret, install the
pinned Flux components and apply the sync resources. Restore shared content
separately when that later capability exists. Git contains desired state, not
Secrets, content, SQLite state or proof of a successful backup.

Upgrade APT packages with APT. For the K3s binary, first check APT availability;
otherwise download the selected official release, verify its checksum, preserve
the previous binary and configuration, and follow upstream upgrade constraints.
Update the recorded pins and Flux/MetalLB manifests through the appropriate
source and operational commits. Back up before a K3s data migration; downgrading
a binary alone may not restore a migrated datastore. Recheck node health, Flux
reconciliation and DNS/UDP after upgrades.
