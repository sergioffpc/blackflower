# Falcor, Slang and PhysX compatibility research

Status: source-based investigation of the owner's selected technologies, 2026-09-07. No dependencies were installed, no candidate was built, and no performance or target-runtime compatibility was established. Exact package versions, graphics backend and exception integration remain decisions to validate.

## Findings that affect the architecture

The owner selected Falcor for rendering, Slang for shaders and PhysX for physics. The updated owner requirement keeps CPU PhysX in the authoritative Linux server and requires GPU PhysX in each Windows client Prediction World, limited to local movement against static geometry. Dynamic state comes from the server. This supersedes the earlier server-only physics proposal: Windows GPU cross-build/runtime work is now necessary. See [ADR-0002](../adr/0002-separate-client-worlds-and-input.md); integration remains unimplemented.

The principal integration uncertainty is **Falcor's existing Windows build on a Linux host**. Its upstream configuration assumes Windows tooling when the target is Windows. A second concrete issue is **Falcor's exception-based API versus project-owned code compiled without exceptions**. Both can be investigated while retaining the selected technologies; neither should be reported as already solved or inherently impossible.

## Falcor: concrete integration work

The [8.0 top-level CMake source](https://github.com/NVIDIAGameWorks/Falcor/blob/8.0/CMakeLists.txt) makes platform decisions using the **target** system. When Windows is the target, it executes `tools/packman/packman.cmd` during configuration and `build_scripts/deploycommon.bat` during the build. A Linux host cannot use this unmodified command path merely because xwin supplies Windows SDK headers. Adapt dependency acquisition and deployment to choose Linux host tools while acquiring Windows target artifacts.

The same configuration discovers Python Interpreter and Development components together. Its [core target configuration](https://github.com/NVIDIAGameWorks/Falcor/blob/8.0/Source/Falcor/CMakeLists.txt) builds Falcor as a shared library, links `pybind11::embed`, and generates a Python module with Windows post-build commands. Separate host Python used for tooling from target Python headers/libraries/runtime, and decide which Python-related outputs are required by the embedded client. Do not assume disabling an application UI removes the framework's embedding dependency.

Falcor uses Packman binary dependencies, including a bundled dependency collection, Slang, Python, DXC and rendering SDKs. [Its manifest](https://github.com/NVIDIAGameWorks/Falcor/blob/8.0/dependencies.xml) pins package versions. **Proposal:** package the selected framework and required artifacts through a reviewed vcpkg overlay, retaining source/archive hashes and patches. Integrating Packman wholesale as an independent resolver would need an explicit dependency-policy decision. There is no evidence here that the stock framework is a small drop-in static vcpkg component.

Falcor's [core CMake source](https://github.com/NVIDIAGameWorks/Falcor/blob/8.0/Source/Falcor/CMakeLists.txt) requests C++17 and exports several compile options, public libraries and definitions to consumers. C++17 is an upstream minimum rather than evidence against C++23; verify the selected public headers and templates under Blackflower's Clang 21/C++23 settings. Keep Falcor build options and its transitive types out of the authoritative simulation targets.

### Exception boundary

Falcor's [public Error.h](https://github.com/NVIDIAGameWorks/Falcor/blob/8.0/Source/Falcor/Core/Error.h) declares `RuntimeError`, `AssertionError`, throwing check helpers, and a `catchAndReportAllExceptions` template containing `try`/`catch`. The framework cannot be described as exception-free. Compiling third-party Falcor with its own flags does not by itself prevent an exception from escaping into Blackflower code.

**Proposed resolution for owner review:** a narrow Falcor adapter compiled with exceptions enabled, catching dependency failures and returning explicit results before control crosses into the no-exception application core. It must also contain any throwing callbacks, keep ownership/destruction on the appropriate side, and verify both ordinary API and shutdown failures. An application-owned adapter using `try`/`catch` is a project policy exception; do not silently create it under the current rules. The owner's selection of Falcor does not itself settle that policy choice. An upstream adaptation is another possible route, but its cost and completeness have not been demonstrated.

### Rendering and shader execution

Falcor's [ProgramManager](https://github.com/NVIDIAGameWorks/Falcor/blob/8.0/Source/Falcor/Core/Program/ProgramManager.cpp) invokes Slang compilation and reflection APIs at runtime. Consequently, choosing Slang is aligned with the framework, but adding a Linux-host shader compiler does not replace the Windows-side Slang dependencies required by this integration.

Keep three artifacts distinct: the Linux-host tools, the Windows client libraries, and shader code or shader binaries. Slang's [compiler documentation](https://shader-slang.org/slang/user-guide/compiling.html) describes target-dependent compilation and downstream compilers; its [getting-started guide](https://docs.shader-slang.org/en/stable/external/slang/docs/user-guide/01-get-started.html) documents required companion runtime libraries. Those current docs are useful concepts, but the actual names and behavior must be checked against the selected 2024.1.34 distribution.

**Proposal:** choose one Falcor backend for the Windows MVP and exercise its complete shader creation path, initially with the paired Slang version. Treat DirectX 12 versus Vulkan, startup compilation/caching and runtime artifact deployment as explicit integration decisions. No source review establishes 16.7 ms frame p95 on four simultaneous clients; warm-up and any runtime shader compilation must be recorded in the measurement procedure.

## PhysX: Linux CPU simulation

PhysX supplies a [kinematic capsule character controller](https://nvidia-omniverse.github.io/PhysX/physx/5.7.0/docs/CharacterControllers.html) with collision-and-slide behavior and [scene ray/overlap/sweep queries](https://nvidia-omniverse.github.io/PhysX/physx/5.7.0/docs/SceneQueries.html). Those APIs address the MVP's movement blocking, free entry points and immediate virtual-hit tests. Controller dimensions, contact offset, query filtering and player-to-player behavior still need explicit tests; feature availability is not proof of the agreed no-pushing behavior.

The controller documentation defines capsule height as the distance between its sphere centers and exposes a separate contact skin. For the agreed total height of 1.8 m and diameter of 0.6 m, configure the corresponding cylinder height and radius consistently with rendering and hit queries. Numerical contact tolerance must not silently enlarge the accepted hit volume. Disable step climbing and other behavior outside the flat-scene MVP when configuring the controller. These are proposed integration checks based on the same [controller documentation](https://nvidia-omniverse.github.io/PhysX/physx/5.7.0/docs/CharacterControllers.html).

PhysX 5.5.0's [Linux CMake source](https://github.com/NVIDIA-Omniverse/PhysX/blob/106.4-physx-5.5.0/physx/source/compiler/cmake/linux/CMakeLists.txt) explicitly configures `-fno-exceptions`, `-fno-rtti` and Clang-specific options. This is useful compatibility evidence, but no Clang 21 build or C++23 consumer test was performed. Retain third-party compiler options within its targets, translate errors through the SDK's documented mechanisms, and verify callback lifetime and allocation policy.

The current [vcpkg recipe](https://github.com/microsoft/vcpkg/blob/9e593bb18ea69cc5095e012465dcd675a822ed0d/ports/physx/portfile.cmake) downloads prebuilt PhysX GPU packages even for Linux and disables snippets/PVD runtime. This download does not mean CPU physics needs a GPU at runtime. For a clean CPU-only dependency closure, assess a reviewed overlay using the explicit `PX_GENERATE_GPU_PROJECTS=OFF` route in the [5.9.0 source CMake](https://github.com/NVIDIA-Omniverse/PhysX/blob/110.1-omni-and-physx-5.9.0/physx/CMakeLists.txt), which omits CUDA language/GPU target generation. Validate the selected revision and do not copy options from 5.9 into 5.5 without checking their existence.

For the now-required Windows physics, the current vcpkg recipe requests MSBuild and the [5.5.0 Windows configuration](https://github.com/NVIDIA-Omniverse/PhysX/blob/106.4-physx-5.5.0/physx/source/compiler/cmake/windows/CMakeLists.txt) emits MSVC-style flags. That is an additional custom-toolchain concern, **now relevant to the required GPU client prediction path**. The port itself says it is not officially supported by NVIDIA.

The Linux server's runtime ABI still needs attention: the repository [build baseline](../build.md) uses Ubuntu 26.04/libstdc++ 15.2.0, while the reference deployment is Debian. The GCC [ABI guidance](https://gcc.gnu.org/onlinedocs/libstdc++/manual/abi.html) explains that binaries using newer library symbols are not guaranteed to work with older libraries. Build against an appropriate deployment environment/sysroot or explicitly package and verify the runtime. Static PhysX linkage alone does not solve every system-library dependency.

## Follow-up: GPU prediction requirement

The owner subsequently required two client worlds and GPU prediction against static geometry only. PhysX 5.5 documents GPU rigid-body stages and CPU scene queries; the character-controller algorithm uses collision queries. Enabling a GPU scene therefore does not by itself establish GPU character movement. A GPU rigid-body movement implementation needs a dedicated behavior and runtime proof before selecting the controller approach. Sources: [PhysX 5.5 GPU simulation](https://nvidia-omniverse.github.io/PhysX/physx/5.5.0/docs/GPURigidBodies.html), [character controllers](https://nvidia-omniverse.github.io/PhysX/physx/5.5.0/docs/CharacterControllers.html).

Verify the GPU binary package, CUDA/driver compatibility on the RTX 5070 Ti, actual device execution, and four-client rendering contention. Do not infer cross-platform numerical identity or performance benefit from GPU activation. An available CPU fallback is not evidence that the owner's GPU requirement is met. No new build or runtime experiment has been performed by this documentation update.
