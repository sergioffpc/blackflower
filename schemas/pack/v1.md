# Platform-independent scenario pack v1

Status: implemented. This is the byte contract shared by the cooker and runtime
reader. The [scene schema](../scene/v1.md) defines the primitive payload.

All integers are little-endian, with explicit widths and no native struct
padding. Lengths and offsets are unsigned. There are no policy size caps on
packs, manifests, provenance strings, or source files. Encoded integer widths,
actual available bytes, platform representability, and schema structure still
constrain valid input. The primitive format requires exactly one resource. Every
byte must belong to the header, manifest, a resource, or signature; there is no
padding, compression, trailing data, or algorithm negotiation.

## Header (108 bytes)

| Offset | Size | Value                                                         |
| ------ | ---- | ------------------------------------------------------------- |
| 0      | 8    | ASCII `BFPACK1` followed by a zero byte                       |
| 8      | 4    | Format version, 1                                             |
| 12     | 4    | Role: 1 simulation, 2 presentation                            |
| 16     | 4    | Resource count                                                |
| 20     | 8    | Exact total file size                                         |
| 28     | 8    | Manifest size                                                 |
| 36     | 8    | Combined payload size                                         |
| 44     | 32   | Signing key identifier: SHA-256 of the raw Ed25519 public key |
| 76     | 32   | Scenario build identity                                       |

The caller supplies the required content role independently of the artifact.
Simulation content serves simulation and prediction; presentation content serves
presentation. Packs contain no platform, processor architecture or deployment
profile. Resource types and schemas define their representation and
compatibility.

## Manifest

A u32 provenance length, the provenance bytes, then exactly resource-count
64-byte records. Each record contains u32 resource identity, u32 type, u32
schema, u32 reserved (zero), u64 payload-relative offset, u64 size, and the
32-byte SHA-256 of that resource. Identities are positive and strictly
increasing. Payload ranges are nonempty, contiguous in record order, begin at
zero, and cover the entire payload. Unsupported types/schemas are rejected.
Version 1 requires exactly one scene entry: identity 1, type 1, schema 1.

Provenance is the 32-byte hash of the exact source file, the 32-byte settings
hash, then five length-prefixed strings (u32 byte length followed by printable
ASCII bytes): cooker revision, Python version, cryptography version, and that
backend's OpenSSL version, and OpenUSD version. Strings are nonempty. No
pathname, timestamp, private key, or host name is recorded. The cooker revision
is `primitive-usd-v1`; any change to output semantics must change that revision.
Settings bytes are the literal ASCII
`primitive-usd-v1;units=mm;simulation=1;presentation=2`.

The common scenario build identity is SHA-256 of ASCII
`Blackflower.ScenarioBuild.v1` plus a zero byte, followed by the exact
provenance bytes, then both roles' resource summaries in simulation/presentation
order. Each summary is u32 role, u32 resource count, followed by each resource's
u32 identity/type/schema, u64 size and 32-byte digest in identity order.
Signatures, final pack identities and the build identity itself are excluded.
The cooker recomputes this identity when verifying the finished pair; each
standalone reader authenticates it without requiring the other artifact.

## Authentication and trust

The final 64 bytes are a detached Ed25519 signature of ASCII
`Blackflower.Pack.v1` plus a zero byte, followed by the exact header and
manifest bytes. Payload integrity is bound by the signed digests. PackId is
SHA-256 of that same transcript. Ed25519 is the ordinary one-shot variant, not
Ed25519ph. Verify actual bytes, never a reserialized manifest.

Trust comes from a separately provisioned public-key set passed by the
application. A key carried by the pack cannot authorize it. The test harness
accepts a raw 32-byte public-key file explicitly; product applications will
provision their own trust set. Private keys remain outside the repository and
delivery; test keys are disposable and never become production trust.

Map the file read-only and retain ownership of the mapping. Validate ranges
against actual bytes using overflow-safe arithmetic before taking slices, verify
signature and digests, validate schema encoding, and only then return immutable
prepared content retaining access to the authenticated bytes. No ECS world or
SDK is created here.

## Pair publication

The Linux cooker requires a new output directory. It stages exactly
`mvp.bfsimulation` and `mvp.bfpresentation` in a private sibling directory,
reads and verifies both completed files independently, checks their shared
identity and scene values, and renames the directory to publish the pair.
Existing output is rejected, never overwritten. Failures before the rename leave
no new published pair. Console success follows publication. This is a
process-failure guarantee on one local filesystem, not a power-loss durability
or distributed-storage transaction guarantee.

## Format compatibility

Schema versions change only with a major project release. During development,
update this contract in place and regenerate artifacts when its encoding
changes. See the
[schema versioning policy](../../docs/development-process.md#schema-versioning).

File ingestion uses read-only mappings on Linux and Windows, avoiding a complete
heap copy. Hash verification still touches the entire payload. Decoded scene
collections and the header/manifest signature transcript use separate memory.
The caller must keep backing files unchanged while mappings exist. Windows holds
a handle denying writes and deletion; Linux requires immutable publication and
deployment. Mapping is not a snapshot. See
[ADR-0011](../../docs/adr/0011-map-content-files.md).

Platform representability and available resources still constrain ingestion; no
policy byte cap or recoverable allocation-failure guarantee is introduced.
