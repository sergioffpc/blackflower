# Minimal scenario pack v1

Status: implemented by ticket #21; runtime SDK resources are added by later
schemas. This document is the byte contract, independent of either reader.

All integers are little-endian, with explicit widths and no native struct
padding. Lengths and offsets are unsigned. There are no policy size caps on
packs, manifests, provenance strings, or source files. Encoded integer widths,
actual available bytes, platform representability, and schema structure still
constrain valid input. The primitive profile requires exactly one resource.
Every byte must belong to the header, manifest, a resource, or signature; there
is no padding, compression, trailing data, or algorithm negotiation.

## Header (112 bytes)

| Offset | Size | Value                                                         |
| ------ | ---- | ------------------------------------------------------------- |
| 0      | 8    | ASCII `BFPACK1` followed by a zero byte                       |
| 8      | 4    | Format version, 1                                             |
| 12     | 4    | Role: 1 client, 2 server                                      |
| 16     | 4    | Profile: 1 Windows x64 primitive-v1, 2 Linux x64 primitive-v1 |
| 20     | 4    | Resource count                                                |
| 24     | 8    | Exact total file size                                         |
| 32     | 8    | Manifest size                                                 |
| 40     | 8    | Combined payload size                                         |
| 48     | 32   | Signing key identifier: SHA-256 of the raw Ed25519 public key |
| 80     | 32   | Scenario build identity                                       |

Only (client, Windows) and (server, Linux) role/profile pairs are supported. The
caller supplies its expected role/profile independently of the file. These
profiles describe prepared primitives, not validated PhysX or graphics SDK
compatibility. Additional required SDK resource schemas need new profiles.

## Manifest

A u32 provenance length, the provenance bytes, then exactly resource-count
64-byte records. Each record contains u32 resource identity, u32 type, u32
schema, u32 reserved (zero), u64 payload-relative offset, u64 size, and the
32-byte SHA-256 of that resource. Identities are positive and strictly
increasing. Payload ranges are nonempty, contiguous in record order, begin at
zero, and cover the entire payload. Unsupported types/schemas are rejected.
Version 1 requires exactly one scene entry: identity 1, type 1, schema 1.

Provenance is the 32-byte hash of the exact source file, the 32-byte settings
hash, then five length-prefixed strings (u32 byte length followed by printable
ASCII bytes): cooker revision, Python version, cryptography version, and that
backend's OpenSSL version, and OpenUSD version. Strings are nonempty. No
pathname, timestamp, private key, or host name is recorded. The cooker revision
is `primitive-usd-v1`; any change to output semantics must change that revision.
Settings bytes are the literal ASCII
`primitive-usd-v1;units=mm;client=1;server=2`.

The common scenario build identity is SHA-256 of ASCII
`Blackflower.ScenarioBuild.v1` plus a zero byte, followed by the exact
provenance bytes, then both roles' resource summaries in client/server order.
Each summary is u32 role, u32 profile, u32 resource count, followed by each
resource's u32 identity/type/schema, u64 size and 32-byte digest in identity
order. Signatures, final pack identities and the build identity itself are
excluded. The cooker recomputes this identity when verifying the finished pair;
each standalone reader authenticates it without requiring the other artifact.

## Authentication and trust

The final 64 bytes are a detached Ed25519 signature of ASCII
`Blackflower.Pack.v1` plus a zero byte, followed by the exact header and
manifest bytes. Payload integrity is bound by the signed digests. PackId is
SHA-256 of that same transcript. Ed25519 is the ordinary one-shot variant, not
Ed25519ph. Verify actual bytes, never a reserialized manifest.

Trust comes from a separately provisioned public-key set passed by the
application. A key carried by the pack cannot authorize it. The test harness
accepts a raw 32-byte public-key file explicitly; product applications will
provision their own trust set. Private keys remain outside the repository and
delivery; test keys are disposable and never become production trust.

Read the file once into owned storage. Validate ranges against actual bytes
using overflow-safe arithmetic before taking slices, verify signature and
digests, validate schemas and scene semantics, and only then return immutable
prepared content owning those exact bytes. No ECS world or SDK is created here.

## Pair publication

The Linux cooker requires a new output directory. It stages exactly
`mvp.bfclient` and `mvp.bfserver` in a private sibling directory, reads and
verifies both completed files independently, checks their shared identity and
scene values, and renames the directory to publish the pair. Existing output is
rejected, never overwritten. Failures before the rename leave no new published
pair. Console success follows publication. This is a process-failure guarantee
on one local filesystem, not a power-loss durability or distributed-storage
transaction guarantee.

## Size-policy compatibility

[ADR-0009](../../docs/adr/0009-typed-errors-and-content-size-policy.md) removes
implementation policy caps without changing field widths, signed transcripts, or
the default cooker output. Existing valid artifacts remain valid and keep their
identities. Older readers still reject artifacts exceeding their former caps;
deploy updated readers before distributing such content. The loader keeps the
complete file and a signature transcript in memory; no streaming guarantee or
recoverable allocation-failure guarantee is introduced.
