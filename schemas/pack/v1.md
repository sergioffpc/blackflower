# Platform-independent scenario pack v1

Status: implemented. This is the byte contract shared by the cooker and runtime
reader. The [scene schema](../scene/v1.md) defines the entity payload.

All integers are little-endian, with explicit widths and no native struct
padding. Lengths and offsets are unsigned. There are no policy size caps on
packs, manifests, provenance strings, or source files. Encoded integer widths,
actual available bytes, platform representability, and schema structure still
constrain valid input. The initial format requires exactly one resource. Every
byte must belong to the header, manifest, a resource, or signature; there is no
padding, compression, trailing data, or algorithm negotiation.

## Header (104 bytes)

| Offset | Size | Value                                                         |
| ------ | ---- | ------------------------------------------------------------- |
| 0      | 8    | File-type magic from the table below                          |
| 8      | 4    | Format version, 1                                             |
| 12     | 4    | Resource count                                                |
| 16     | 8    | Exact total file size                                         |
| 24     | 8    | Manifest size                                                 |
| 32     | 8    | Combined payload size                                         |
| 40     | 32   | Signing key identifier: SHA-256 of the raw Ed25519 public key |
| 72     | 32   | Content build identity                                        |

| Extension   | Magic bytes                             | Decoded scene |
| ----------- | --------------------------------------- | ------------- |
| `.bfserver` | ASCII `BFSERV1` followed by a zero byte | `ServerScene` |
| `.bfagent`  | ASCII `BFAGNT1` followed by a zero byte | `AgentScene`  |
| `.bfclient` | ASCII `BFCLNT1` followed by a zero byte | `ClientScene` |

The magic identifies the concrete scene contract and is authenticated as part of
the header. The loader selects the scene variant from these bytes, independent
of the filename. Resource schemas define representation compatibility. No
separate role field, caller-supplied type, or platform profile is required.

## Manifest

A u32 provenance length, the provenance bytes, then exactly resource-count
64-byte records. Each record contains u32 resource identity, u32 type, u32
schema, u32 reserved (zero), u64 payload-relative offset, u64 size, and the
32-byte SHA-256 of that resource. Identities are positive and strictly
increasing. Payload ranges are nonempty, contiguous in record order, begin at
zero, and cover the entire payload. Unsupported types/schemas are rejected.
Version 1 requires exactly one scene entry: identity 1, type 1, schema 1.

Provenance is the 32-byte hash of the source dependency transcript, the 32-byte
settings hash, then five length-prefixed strings (u32 byte length followed by
printable ASCII bytes): cooker revision, Python version, cryptography version,
and that backend's OpenSSL version, and OpenUSD version. Strings are nonempty.
No absolute pathname, timestamp, private key, or host name is recorded. The
role-scene cooker revision token is `role-scenes-v1`. The settings bytes are the
literal ASCII
`role-scenes-v1;units=m-f64;colliders=local;components=sparse;scenes=server,agent,client`.
They distinguish the sparse role projection from earlier development output.

The source transcript starts with ASCII `Blackflower.USDSource.v1` and a zero
byte. Its records sort by logical name: "." identifies the root scene, and
normalized POSIX paths relative to its directory identify referenced layers.
Each record contains u32 UTF-8 name length, name bytes, u64 raw file size and
SHA-256 of the exact captured file bytes. Each logical dependency is recorded
once. Absolute checkout paths are excluded, so moving the same directory tree
does not affect identity. Whitespace edits and definition edits do affect it.

The content build identity is SHA-256 of ASCII `Blackflower.ScenarioBuild.v1`
plus a zero byte, followed by the exact provenance bytes and the server, agent
then client resource summaries. Each summary contains u32 resource count, then
each resource's u32 identity/type/schema, u64 size and 32-byte digest in
identity order. No purpose tag is encoded. Signatures and the build identity
itself are excluded. The cooker recomputes the shared identity from the finished
set; each runtime loader authenticates its pack's signed value.

## Authentication and trust

The final 64 bytes are a detached Ed25519 signature of ASCII
`Blackflower.Pack.v1` plus a zero byte, followed by the exact header and
manifest bytes. Payload integrity is bound by the signed digests. Ed25519 is the
ordinary one-shot variant, not Ed25519ph. Verify actual bytes, never a
reserialized manifest.

Trust comes from a separately provisioned public-key set passed by the
application. A key carried by the pack cannot authorize it. The test harness
accepts a raw 32-byte public-key file explicitly; product applications will
provision their own trust set. Private keys remain outside the repository and
delivery; test keys are disposable and never become production trust.

Map the file read-only and retain ownership of the mapping. Validate ranges
against actual bytes using overflow-safe arithmetic before taking slices, verify
signature and digests, validate schema encoding, and only then return immutable
prepared content retaining access to the authenticated bytes. No ECS world or
SDK is created here.

## Publication

The Linux cooker requires a new output directory. It stages `.bfserver`,
`.bfagent` and `.bfclient` files named from the source stem in a private sibling
directory. It reads and verifies all completed files, checks their shared build
identity and scene values, and renames the directory to publish the set.
Existing output is rejected, never overwritten. Failures before the rename leave
no new published set. Console success follows publication. This is a
process-failure guarantee on one local filesystem, not a power-loss durability
or distributed-storage transaction guarantee.

The extensions guide application file selection. Loading infers the concrete
scene type from the authenticated magic rather than the extension. The public
C++ scene value is `std::variant<ServerScene, AgentScene, ClientScene>`; its
alternative matches the file type. Distinct file types have distinct signed
transcripts even when their scene collections are identical. A caller may also
require an expected role, which is compared only after authentication, integrity
checking and scene decoding.

## Format compatibility

Schema versions change only with a major project release. During development,
update this contract in place and regenerate artifacts when its encoding
changes. See the
[schema versioning policy](../../docs/development-process.md#schema-versioning).

File ingestion uses read-only mappings on Linux and Windows, avoiding a complete
heap copy. Hash verification still touches the entire payload. Decoded scene
collections and the header/manifest signature transcript use separate memory.
The caller must keep backing files unchanged while mappings exist. Windows holds
a handle denying writes and deletion; Linux requires immutable publication and
deployment. Mapping is not a snapshot. See
[ADR-0011](../../docs/adr/0011-map-content-files.md).

Platform representability and available resources still constrain ingestion; no
policy byte cap or recoverable allocation-failure guarantee is introduced.
