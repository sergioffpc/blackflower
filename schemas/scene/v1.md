# Scene v1

The scene payload is an immutable, role-specific list of
`SceneEntityDescription` records in a `SceneAsset`. Each description owns its
authored `SceneEntityId`, placement, and the sparse collision or presentation
domains required by that role. There is no mutable scene graph, global
collection, light/spawn collection, media data, or training objective in this
format.

## Coordinates and encoding

Coordinates use metres in a right-handed frame: X right, Y up, positive Z
completes the frame. The bounded USD input already uses this convention; other
units and up axes are rejected rather than silently converted. All integers are
little-endian unsigned values; geometry uses little-endian IEEE 754 binary64.
Rotations are unit quaternions in XYZW order.

The payload starts with a u32 scene-entity-description count, followed by
complete description records. An empty scene occupies four bytes. No padding or
trailing bytes are permitted. Integer widths define representability; no policy
count cap applies. Consumers allocate only as records are successfully decoded.

Each `SceneEntityDescription` record starts with these fields in order:

| Field          | Encoding                             |
| -------------- | ------------------------------------ |
| ID byte length | u32                                  |
| SceneEntityId  | That many ASCII bytes, no terminator |
| Position       | Three binary64 coordinates           |
| Rotation       | Four binary64 quaternion components  |
| Uniform scale  | One binary64 value                   |
| Component mask | u32                                  |

IDs match case-sensitive `[A-Za-z0-9][A-Za-z0-9_.:-]*`, are unique within the
scene, and sort in strictly increasing ASCII order. They identify scene entities
independently of USD prim paths. Projection never renumbers an entity: the same
authored entity retains the same ID in every role and client domain where it
appears. The fixed portion occupies 72 bytes, excluding the ID and component
records.

Mask bit 0 declares collision, bit 1 declares a logical visual reference, and
bit 2 declares a logical audio reference. Other bits and a zero mask are
invalid. Component data follows in bit order. `ServerScene` and `AgentScene`
permit only collision-bearing descriptions. `ClientScene` contains the union of
static-collision, visual, and audio descriptions; any combination of the three
supported components is valid. Descriptions with no component for a role are
omitted rather than encoded as placeholders.

The collision component starts with a u32 domain and u32 collider count. Domain
1 is `SessionStatic`; other values and an empty collider collection are
rejected. The current authoring subset produces only `SessionStatic` collision.
The count is followed by that many collider records.

Each collider starts with a u32 kind. Kind 1 is an oriented box, followed by
three binary64 entity-local centre coordinates, three binary64 full dimensions
and four binary64 XYZW rotation components: 84 bytes in total. Other kinds are
rejected. Collider records sort by their authored child prim names. Containment
identifies the owning scene entity; no separate owner index or persistent
collider ID is serialized.

All numeric fields must be finite; dimensions and scale must be positive.
Quaternion squared norm must differ from one by at most 1e-12. The loader
validates identities, transforms, component masks, role restrictions, collision
domains, kinds, references, and byte boundaries before publishing a complete
description. Physical suitability remains a consumer decision.

The visual and audio components each contain a u32 byte length followed by one
logical ASCII reference with no terminator. References use the same grammar as
`SceneEntityId`. They identify future adapter-owned presentation resources; this
schema does not contain model, material, texture, clip, or emitter data.

## Identities and shared resources

AssetId is a 32-byte SHA-256 digest, distinct from the pack-set ContentBuildId.
Its encoding is derived from authenticated bytes rather than stored redundantly:

-   SceneAsset: SHA-256 of ASCII `Blackflower.Scene.v1` immediately followed by
    the complete scene payload.
-   ColliderAsset: SHA-256 of ASCII `Blackflower.Collider.v1` immediately
    followed by the owning scene entity's u32 collider count and collider
    records. The collision-domain value is excluded.

These two identity domains have **no terminating zero byte**. IDs cover exact
compiled bits; numerically equivalent but differently encoded floating-point
values need not deduplicate. Scene identity excludes pack role, signatures and
source provenance; collision identity also excludes placement and
`SceneEntityId`. Thus definition reuse at different placements shares one
immutable collider resource. The verified provenance still records every
captured source and setting through the pack contract. Equal IDs with unequal
decoded descriptions or collider values are rejected by `ResourceManager` before
publication. All-zero `AssetId` is reserved; runtime handles never use digest
values as generations.

The dependency list is implicit in the descriptions' derived collider identities
and logical presentation references. This slice has one whole-scene residency
unit and no Parent/reference patches. `ServerScene` and `AgentScene` physically
omit presentation-only data. `ClientScene` physically contains both its
Prediction collision input and Presentation references. Each pack remains
independently verified and complete. Runtime lifetimes are in
[runtime scenes](../../docs/runtime-scenes.md).

`SceneEntityId` is persistent only within its scene namespace. Live lookup
requires `(SceneInstance, SceneEntityId)`. ECS `Entity` and resource handles are
typed runtime identities with generation checks; they are never serialized.
Unload and reuse cannot turn an old handle into a new valid reference.

## Placement and migration

The #58 revision stored world-space `Bound` records. The #61 revision evolves
schema 1 in place to **entity-local Collider** records and regenerates fixtures;
the #78 revision adds sparse component masks, the `SessionStatic` collision
domain, and logical presentation references. There is no legacy decoder. Re-cook
source assets when moving between these revisions. Do not feed earlier
development packs to the new runtime.

The USD authoring scope remains `Bounds` and still means independently authored
collision. It maps to cooked colliders, never to visual LocalBounds/WorldBounds.
The cooker now encodes each Cube's local transform, without composing its entity
placement. Identity definition roots and non-transforming Bounds scopes make
this separation exact for the supported subset. Cube scale is baked into full
box dimensions; entity scale stays in placement.

At instantiation, `root * placement` becomes the root entity's authoritative
LocalTransform in world space. WorldTransform is derived from that value. World
collider centres use `translation + rotation(localCentre * scale)`; dimensions
use `localDimensions * scale`; orientation uses `worldRotation * localRotation`.
Placement is applied exactly once. Root options are initial placement, not a
retained Parent or second mutable authority.

The rotated/scaled fixture reconstructs the earlier world-space geometry, then
adds an independent instance root. Analytical fixture tolerances are 1e-9 metres
for positions/dimensions and 1e-12 for quaternion components. Nonrepresentable
runtime transforms return a typed error without publishing partial entities.

## OpenUSD authoring

The cooker captures the scene and its directly referenced entity definition
layers before composition. The [authoring contract](../../docs/usd-authoring.md)
defines `/Scene/Entities`, reusable `/Entity` definitions and authored `Bounds`.
An absent Entities scope yields an empty scene. An absent Bounds scope means no
collision component; absent logical presentation attributes mean no
corresponding reference. A description absent from every domain is omitted from
all role payloads. Actual visual/audio media import remains pending. Source USD
and Python are not runtime dependencies.

Schema evolution follows the
[release policy](../../docs/development-process.md#schema-versioning).
